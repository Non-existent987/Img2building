## 一、先说清楚要解决什么问题

做GIS 的朋友大概都干过这件事：接到一片范围，需要把里面的建筑物轮廓变成矢量图层。

最传统的方法是在Google Earth 或影像底图上手工描边。慢是慢了点，但它有个致命问题——**不可复现**。同一片区域，第二个人做出来的结果和第一个不一样；三个月后再做一次，又不一样。只要你的工作涉及面积统计、变化检测、覆盖率分析，这个不确定性就会一路传导到结论里去。

商业 API（如某家的建筑物提取服务）能解决，但按量计费，做整城级别的批量提取成本会很难看，而且数据出境在国内还有合规问题。

所以我在做这个开源项目：**框选一片区域，模型自动提取建筑轮廓，直接导出 SHP。**

## 三、怎么用

### 输入方式

三种，覆盖不同场景：

- **框选**：拖一个矩形，批量提取范围内所有建筑。适合成片区域处理
- **点选**：点单个坐标，提取那一个建筑。适合补漏
- **经纬度定位**：直接输入坐标跳转。适合你手上已经有一份坐标清单，要逐个核对的场景

### 输出

导出 Shapefile，完整 GIS 属性结构。拖进 QGIS / ArcGIS 就是普通矢量图层，能叠加、能做统计、能出图。

### 校正

这个必须说清楚：**模型识别是辅助，不是替代**。

工具提供了手动编辑轮廓和增补标记点的能力，用于修正漏检误检。我的经验是，判断一栋建筑是不是"漏了"，最快的办法就是导出后拿原始影像过一遍——肉眼比对永远比相信模型靠谱。

自动化的价值在于把80% 的常规工作压缩掉，而不是 100% 免掉人工。

## 四、技术实现

| 层 | 选型 |
|---|---|
| 前端 | Vue 3 + TypeScript + Vite 4 + Leaflet 1.9 |
| 后端 | FastAPI + PyTorch |
| 数据 | 自建数据集，8000+ 标注影像 |

选 FastAPI 是因为推理服务本身就是 IO 密集型的 API 服务，异步原生支持省事。前端用 Leaflet 而非 Mapbox，因为不需要商业地图 token，瓦片源可以自由切换。

## 五、项目地址

>本文项目地址：github.com/Non-existent987/Img2building

MIT 协议开源。仓库里有完整的前端源码和运行说明。

**关于模型权重**：约 226MB，超出 GitHub 单文件 100MB 的硬限制，所以没有随仓库分发。托管地址会在 README 里更新。顺带说一句，Git LFS 免费版每月只有 10GB 下载带宽，一个 226MB 的模型意味着 45 个人完整下载就触顶了，之后 GitHub 会直接禁用整个账号的 LFS 下载直到次月——对公开项目来说这是个陷阱，不建议用 LFS 分发模型。

## 七、一点碎碎念

做这个项目最大的体会是：**模型精度和工程可用性是两件事**。

一个mIoU 刷到很高的模型，如果单张图要跑 30 秒、结果还要手工修半天，那它不如一个精度低 5 个点但能批量跑的模型有用。

GIS 从业者要的是"能用"，不是"指标好看"。整个工具的设计都是围绕这个来的。
